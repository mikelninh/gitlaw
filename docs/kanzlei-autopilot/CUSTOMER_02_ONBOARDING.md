# Kanzlei Autopilot — Customer #2 onboarding template

This is intentionally customer-neutral. A new Kanzlei must not require a new fork of GitLaw.

## 1. Select one workflow

Choose one recurring, measurable workflow. Prefer high-frequency preparation work before consequential legal action.

Default first candidate: `migration/document-readiness`.

## 2. Create customer configuration

Customer-specific configuration contains only:

- pseudonymous tenant/customer ID;
- roles and accountable owner;
- approved templates;
- approved document checklists;
- allowed systems/connectors;
- exact authority envelope;
- data-mode/privacy release state;
- credentials stored outside source control.

Do not copy customer names, secrets or credentials into a Workflow Pack.

## 3. Start at P0/P1

- P0: synthetic/historic proof.
- P1: controlled real-mandate Shadow mode with no consequential external execution.

Production AI/cloud access is not inferred from technical availability.

## 4. Establish baseline

Measure active human minutes before automation. Do not estimate savings from task counts alone.

## 5. Run 10–20 representative cases

For each run record:

- active pilot minutes;
- correction/rework minutes;
- human-attention item;
- wrong-matter event;
- critical miss;
- authority violation.

## 6. Produce Proof Week report

Use `/#/pro/proof-week` or the reusable report model.

KEEP requires positive confirmed minutes returned plus zero recorded safety failures.

## 7. Decide next workflow

Select by:

`weekly minutes wasted × repeatability × safe-automation potential`.

Do not expand autonomy merely because the customer likes the demo.

## 8. Earn bounded execution

Only after observed evidence supports it, propose moving a narrow action from preparation/approval into bounded execution. The customer explicitly approves the new authority envelope.
